Auth Flow

Headtilts uses a JWT access + refresh token scheme. Tokens are stored in localStorage on the client and injected via an Axios interceptor.

Token Lifecycle

  • Access token — 15-minute expiry, signed with JWT_SECRET. Sent as Authorization: Bearer <token>.
  • Refresh token — 7-day expiry, stored as a hashed Session record in the database. Used to obtain new access tokens silently.
  • On 401, the Axios interceptor calls POST /auth/refresh and retries the original request.

First-time Setup

On a fresh install, GET /auth/setup-status returns { needsSetup: true }. The admin app redirects to /admin/setup where the first super-admin account is created. After that, the route is permanently disabled.

Password Reset

  1. POST /auth/forgot-password — generates a token, emails a reset link. Silent if email not found.
  2. POST /auth/reset-password — verifies token (sha256 hash), sets new password, revokes all sessions.

Data Models — API Keys

ApiKey

Represents a long-lived secret key belonging to a user, used to authenticate REST API requests from external scripts and integrations. The raw key is shown exactly once at creation; only its SHA-256 hash is stored.

FieldTypeNotes

nameStringHuman-readable label (e.g. "CI pipeline")

keyHashStringSHA-256 hex digest of the raw key. Used for lookup on every request. Unique.
userIdStringFK → User.id. Keys are owned by the creating user.
scopesText (JSON array)Allowed scope strings, e.g. ["posts:read","media:write"]
expiresAtDateTime?Optional expiry. Null = never expires. Checked on every request.
lastUsedAtDateTime?Fire-and-forget updated on each successful request. Null until first use.
activeBooleanSoft-disable without deletion (currently always true; revoke deletes the row).
createdAt / updatedAtDateTimeAuto-managed
Key format: htk_ followed by 64 hex characters (32 random bytes). Total length 68 characters. Never stored plain — only the SHA-256 hash is persisted.

PostRevision

Every create/update creates a revision entry. The changes JSON field stores a structured diff: { field, label, from?, to?, note? }[]. Actions: created, updated, published, unpublished, scheduled, trashed.

PostCoAuthor

Join table for multiple authors. order controls display sequence. Primary author is stored on Post.authorId; co-authors are rows here. Primary author cannot simultaneously be a co-author (enforced on save).

Data Models — Media

Media

Stores file metadata. Physical files are on disk. Generated variants:

  • thumbnailUrl — 150×150 crop (configurable)
  • mediumUrl — 300px max dimension
  • url — optimized/resized main file
  • originalUrl — untouched source (preserved when format conversion is on)

contentHash (SHA-256) enables upload deduplication. mimeType validated against upload_allowed_mime setting.

MediaFolder

Optional grouping for media files. Each folder has a unique name and slug. A Media row has an optional folderId FK; files without a folder appear in the root of the library. Deleting a folder sets folderId to null on contained files (cascade set-null).

Data Models — Taxonomy

Category

Hierarchical. parentId for nested categories. icon stores a Font Awesome class string. showSidebar controls sidebar widget display.

Tag

Flat taxonomy. Tags are created on-the-fly from tagNames[] in the post save flow.

Data Models — Menus & Widgets

Menu / MenuItem

A menu has a unique location (e.g., "primary"). Items can link to: a custom URL, a Post, a Category, or a Tag. Items are nested via parentId and ordered by position.

Widget / WidgetZone

Widgets are reusable content blocks. A zone is a named slot on the frontend (e.g., "sidebar"). Many widgets can be assigned to one zone via WidgetZoneWidget. Widget config is key-value pairs stored in WidgetSetting.

Data Models — Miscellaneous

Notification

User-specific notifications. readAt is null when unread. Indexed on (userId, readAt) for fast unread queries.

Comment / CommentReaction

Comments are threaded via parentId. visitorId is a client-generated anonymous identifier. Reactions are unique per (comment, emoji, visitorId) and toggle on repeat submission.

ContactSubmission

Stores contact form submissions from the public site (POST /public/contact). Fields: name, email, subject, message, isRead (default false). Indexed on (isRead) and (createdAt). Managed in the admin under Contact (requires SETTING_READ).

Celebration

Annual events stored by month/day (no year in the date). year is the birth year or year of passing — optional. Indexed on (month, day) for fast daily queries.

Sitemap / SeoMetadata

Sitemap holds manual entries. The XML generator combines these with auto-discovered posts/pages/categories/tags. SeoMetadata stores Yoast-style readability and SEO scores per post.

Usage example

# List published posts
curl https://your-site.com/api/posts \
  -H "X-API-Key: htk_your_key_here"

# Create a draft post (requires posts:write scope)
curl -X POST https://your-site.com/api/posts \
  -H "X-API-Key: htk_your_key_here" \
  -H "Content-Type: application/json" \
  -d '{"title":"Hello","content":"<p>World</p>","status":"draft"}'

Middleware

authenticate

Supports two authentication methods, checked in order:

  1. API key — if X-API-Key header is present, looks up the SHA-256 hash in the ApiKey table, checks expiry, then infers the required scope from HTTP method + req.baseUrl (e.g. GET /api/posts → posts:read). Returns 401 for invalid/expired keys; 403 if the key lacks the required scope. Synthesises a JWTPayload-compatible object from the owning user's RBAC permissions so downstream requirePermission checks continue to work.
  2. JWT Bearer token — extracts the Authorization: Bearer … header, verifies with JWT_SECRET, attaches decoded payload to req.user. Returns 401 if missing or invalid.

requirePermission(permission)

Factory middleware. After authenticate, checks req.user.permissions[] includes the given string. Returns 403 if not. Super-admins always pass (all permissions granted).

asyncHandler(fn)

Wraps async route handlers so unhandled Promise rejections are forwarded to the global error handler instead of crashing.

errorHandler

Global Express error middleware. Converts ApiError instances to JSON responses. Catches Prisma validation errors and maps them to 400. All other errors return 500 in production.

Celebrations Feature

The Celebrations system allows editors to set up annual artist birthday and remembrance tributes. Visitors see a modal spotlight on their first visit each day.

Data Flow

  1. Editor creates a celebration at Admin → Celebrations with name, type (birthday/remembrance), month, day, optional year and photo.
  2. Public site fetches GET /public/celebrations/today on mount.
  3. API resolves "today" using the timezone setting (via Intl.DateTimeFormat), queries active celebrations matching month + day.
  4. Response includes { date: "YYYY-MM-DD", items: [] }. The date string is the localStorage key for the "seen today" gate.
  5. CelebrationSpotlight checks localStorage['celebration-seen-{date}'] — renders nothing if set. Otherwise shows the modal and sets the flag on close.

Spotlight Behavior

  • Single item: static spotlight card with type-specific animation.
  • Multiple items: auto-rotating carousel (5-second interval), pauses on hover, dot indicators, prev/next arrows.
  • Close methods: X button, backdrop click, or Escape key.
  • All CSS animations are inside @media (prefers-reduced-motion: no-preference).
  • Dark mode fully supported via [data-theme='dark'] overrides on celebration-* classes.

After account creation you are redirected to a site configuration wizard at /admin/wizard. It walks through three steps:

  1. Your site — site title, tagline, admin email, and timezone
  2. Logo — light-mode and dark-mode logo images (via the Media Library)
  3. Done — shortcut links to write your first post, create categories, and build navigation

Every step has a Skip button; all values can be changed later in Settings → General. The wizard only appears once per browser (tracked via localStorage).

Custom Domain & HTTPS

For a production deployment with a real domain and HTTPS, the recommended approach is to place a TLS-terminating reverse proxy (nginx or Caddy) in front of the Docker stack on the host, rather than modifying the nginx container inside Docker.

Option A — Caddy (simplest, automatic HTTPS)

Run Caddy on the host, set HTTP_PORT=8080 in .env, then add a Caddyfile:

mysite.com {
    reverse_proxy localhost:8080
}
caddy run --config Caddyfile

Caddy obtains a Let's Encrypt certificate automatically. Update SITE_URL=https://mysite.com in .env and rebuild:

docker compose up -d --build

Option B — nginx on the host with Certbot

Set HTTP_PORT=8080 in .env, then create a host nginx site config:

server {
    listen 80;
    server_name mysite.com;
    return 301 https://$host$request_uri;
}

server {
    listen 443 ssl;
    server_name mysite.com;

    ssl_certificate     /etc/letsencrypt/live/mysite.com/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/mysite.com/privkey.pem;

    # Must be at least as large as the nginx inside Docker (default 50m).
    # Without this, media uploads return 413 Request Entity Too Large.
    client_max_body_size 50m;

    location / {
        proxy_pass http://127.0.0.1:8080;
        proxy_http_version 1.1;
        proxy_set_header Host              $host;
        proxy_set_header X-Real-IP         $remote_addr;
        proxy_set_header X-Forwarded-For   $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto https;

        # WebSocket pass-through for Socket.IO
        proxy_set_header Upgrade    $http_upgrade;
        proxy_set_header Connection "upgrade";
    }
}
# Get a certificate
sudo certbot --nginx -d mysite.com

# Reload nginx
sudo nginx -s reload

Update your .env with SITE_URL=https://mysite.com, WEB_URL=https://mysite.com, ADMIN_URL=https://mysite.com/admin, then rebuild:

docker compose up -d --build

Operations — What to Back Up

Three categories of data cannot be recovered from the git repository and must be backed up independently. A backup is only useful if it is stored off the server — a backup on the same machine that gets compromised or corrupted is worthless.

CategoryDefault LocationWhy It Matters
MySQL database Configured by DATABASE_URL in .env All posts, pages, users, roles, comments, settings, categories, tags, menus, widgets, celebrations, media metadata, sitemap entries, notifications, contact submissions, sessions, and revisions live here. Losing it means losing everything.
Upload directory apps/api/uploads/ (or $UPLOAD_DIR) The actual binary files — images, documents, videos — uploaded via the Media Library. The database stores metadata and URLs; the files are on disk. If the disk is wiped the media library rows become dead links.
Environment secrets .env (root — Docker) or apps/api/.env (local dev) JWT_SECRET cannot be recovered; losing it means every existing access token and signed preview link becomes unverifiable. DB credentials, SMTP_PASS, and SITE_URL must also be preserved. Store these in a password manager or a secrets vault — never commit them to git.

The codebase itself (Prisma schema, migrations, source files) lives in git and does not need a separate backup strategy beyond a remote repository push.

Backup Commands

Database backup

Use mysqldump with --single-transaction so the dump is consistent without locking tables. The timestamp suffix lets you keep multiple dated copies.

mysqldump \
  --host=127.0.0.1 \
  --user=YOUR_DB_USER \
  --password=YOUR_DB_PASS \
  --single-transaction \
  --routines \
  --triggers \
  --no-tablespaces \
  YOUR_DB_NAME \
  > /backups/db_$(date +%Y%m%d_%H%M%S).sql

If your MySQL server is on a remote host, replace --host=127.0.0.1 with the server's IP address. The resulting .sql file is plain text and can be compressed:

gzip /backups/db_$(date +%Y%m%d_%H%M%S).sql
# produces db_20260617_020000.sql.gz (~10–20% of raw size)

Upload directory backup

Create a compressed archive of the entire uploads folder. The -C flag strips the absolute path prefix so the archive is portable.

UPLOADS_DIR="${UPLOAD_DIR:-/path/to/apps/api/uploads}"

tar -czf /backups/uploads_$(date +%Y%m%d_%H%M%S).tar.gz \
  -C "$(dirname "$UPLOADS_DIR")" \
  "$(basename "$UPLOADS_DIR")"

For large media libraries, consider an incremental rsync instead — only changed files are transferred on each run, which is far faster than repacking the full archive daily:

# Sync uploads to a remote server (fast, incremental)
rsync -az --delete \
  /path/to/apps/api/uploads/ \
  user@backup-server:/backups/headtilts-uploads/

Verify a backup

Always confirm your backup file is complete before relying on it. A zero-byte file or a truncated dump is useless.

# Check the SQL dump ends with the completion marker
tail -5 /backups/db_20260617_020000.sql
# Should end with: -- Dump completed on YYYY-MM-DD HH:MM:SS

# List top-level contents of the uploads archive without extracting
tar -tzf /backups/uploads_20260617_020000.tar.gz | head -20

# For gzipped SQL, verify integrity
gzip -t /backups/db_20260617_020000.sql.gz && echo "OK"

Automating Backups

Cron schedule

Add these entries to crontab -e on the server. Run as the same user that owns the application files. Adjust paths to match your deployment.

# ── Headtilts CMS backup cron ──────────────────────────────────────────────

# Daily database dump at 02:00
0 2 * * * mysqldump --host=127.0.0.1 --user=DB_USER --password=DB_PASS \
  --single-transaction --routines --no-tablespaces DB_NAME \
  | gzip > /backups/db_$(date +\%Y\%m\%d).sql.gz

# Daily uploads archive at 02:15 (offset so both don't peak at once)
15 2 * * * tar -czf /backups/uploads_$(date +\%Y\%m\%d).tar.gz \
  -C /path/to/apps/api uploads

# Delete backups older than 14 days at 03:00
0 3 * * * find /backups -name "db_*.sql.gz"      -mtime +14 -delete
0 3 * * * find /backups -name "uploads_*.tar.gz" -mtime +14 -delete

Note: In crontab, the % character must be escaped as \% when used inside a command string.

Backup script (all-in-one)

Save this as /usr/local/bin/headtilts-backup.sh, make it executable (chmod +x), and call it from cron.

#!/usr/bin/env bash
set -euo pipefail

DB_HOST="127.0.0.1"
DB_USER="YOUR_DB_USER"
DB_PASS="YOUR_DB_PASS"
DB_NAME="YOUR_DB_NAME"
UPLOADS_DIR="/path/to/apps/api/uploads"
BACKUP_DIR="/backups"
OFFSITE_DEST="user@backup-server:/backups/headtilts"
KEEP_DAYS=14

STAMP=$(date +%Y%m%d_%H%M%S)

mkdir -p "$BACKUP_DIR"

echo "[backup] Dumping database..."
mysqldump --host="$DB_HOST" --user="$DB_USER" --password="$DB_PASS" \
  --single-transaction --routines --no-tablespaces "$DB_NAME" \
  | gzip > "$BACKUP_DIR/db_${STAMP}.sql.gz"

echo "[backup] Archiving uploads..."
tar -czf "$BACKUP_DIR/uploads_${STAMP}.tar.gz" \
  -C "$(dirname "$UPLOADS_DIR")" "$(basename "$UPLOADS_DIR")"

echo "[backup] Syncing to offsite..."
rsync -az "$BACKUP_DIR/" "$OFFSITE_DEST/"

echo "[backup] Pruning old backups (>${KEEP_DAYS} days)..."
find "$BACKUP_DIR" -name "db_*.sql.gz"      -mtime +"$KEEP_DAYS" -delete
find "$BACKUP_DIR" -name "uploads_*.tar.gz" -mtime +"$KEEP_DAYS" -delete

echo "[backup] Done: db_${STAMP}.sql.gz + uploads_${STAMP}.tar.gz"

Restore Procedure

Follow these steps in order after a data loss event. Perform the restore on a staging copy first if possible to confirm the backup is valid before touching production.

1 — Stop the application

Prevent new writes from arriving while the restore is in progress.

# If running under systemd
sudo systemctl stop headtilts-api

# If running under pm2
pm2 stop headtilts-api

# If running directly, find and kill the process
pkill -f "tsx src/index.ts"

2 — Restore the database

# If the backup is gzip-compressed
gunzip -c /backups/db_20260617_020000.sql.gz | mysql \
  --host=127.0.0.1 \
  --user=YOUR_DB_USER \
  --password=YOUR_DB_PASS \
  YOUR_DB_NAME

# If the backup is plain SQL
mysql \
  --host=127.0.0.1 \
  --user=YOUR_DB_USER \
  --password=YOUR_DB_PASS \
  YOUR_DB_NAME < /backups/db_20260617_020000.sql

If you are restoring to a fresh MySQL instance, create the database and user first:

CREATE DATABASE headtilts CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci;
CREATE USER 'headtilts'@'localhost' IDENTIFIED BY 'strong-password';
GRANT SELECT, INSERT, UPDATE, DELETE, CREATE, ALTER, INDEX, DROP
  ON headtilts.* TO 'headtilts'@'localhost';
FLUSH PRIVILEGES;

3 — Apply any pending Prisma migrations

If the backup predates recent schema changes, run migrations to bring the schema forward. Prisma tracks applied migrations in the _prisma_migrations table and skips already-applied ones.

pnpm --filter @headtilts/api exec prisma migrate deploy

4 — Restore uploaded files

# Extract the archive back to its original location
tar -xzf /backups/uploads_20260617_020000.tar.gz \
  -C /path/to/apps/api/

# Fix ownership if the API runs as a dedicated user
chown -R headtilts:headtilts /path/to/apps/api/uploads/

5 — Verify and restart

# Confirm the upload directory is populated
ls -lh /path/to/apps/api/uploads/ | head -10

# Start the API
sudo systemctl start headtilts-api
# or
pm2 start headtilts-api

# Tail the logs to confirm clean startup
sudo journalctl -u headtilts-api -f
# or
pm2 logs headtilts-api --lines 50

Incident Response — Site Hijacked

If you suspect an attacker has gained unauthorised access to the CMS, work through these steps immediately and in order. Speed matters — every minute the site is online gives the attacker more time to exfiltrate data or plant persistence mechanisms.

Step 1 — Take the site offline

Block all inbound traffic to the API and admin panel before doing anything else. This stops the attacker from continuing to use any active session and prevents further data changes.

# Stop the application process
sudo systemctl stop headtilts-api

# Block the API port at the firewall (port 3000 by default)
# ufw (Ubuntu)
sudo ufw deny 3000

# iptables
sudo iptables -I INPUT -p tcp --dport 3000 -j DROP

Step 2 — Rotate all credentials immediately

Assume every secret in .env is known to the attacker. Regenerate all of them before restarting the application.

SecretActionEffect
JWT_SECRET Replace with a new random string: openssl rand -hex 32 Invalidates every existing access token and refresh token. All users are forced to log in again. All signed preview links expire immediately.
Database password ALTER USER 'headtilts'@'localhost' IDENTIFIED BY 'new-password'; Prevents DB access via the stolen credential.
SMTP_PASS Revoke the SMTP credential in your mail provider and generate a new one Prevents the attacker from sending mail as your domain.
Server SSH keys If the server itself was accessed, rotate SSH keys and audit ~/.ssh/authorized_keys Removes any backdoor SSH access the attacker may have added. 
# Generate a new JWT_SECRET
openssl rand -hex 32

# Update .env (root) with the new values, then verify:
grep JWT_SECRET .env

Step 3 — Delete all active sessions

Even with a new JWT_SECRET, old refresh tokens stored in the Session table become cryptographically invalid. Truncate the table to be certain:

-- Connect to MySQL and run:
TRUNCATE TABLE Session;

Step 4 — Audit user accounts

Look for accounts the attacker may have created or promoted to super-admin.

-- List all active users with their roles
SELECT u.id, u.username, u.email, u.createdAt, GROUP_CONCAT(r.name) AS roles
FROM User u
LEFT JOIN UserRole ur ON ur.userId = u.id
LEFT JOIN Role r      ON r.id = ur.roleId
WHERE u.isActive = TRUE
GROUP BY u.id
ORDER BY u.createdAt DESC;

-- Deactivate any account you do not recognise
UPDATE User SET isActive = FALSE WHERE id = 'suspicious-user-id';

-- Or delete it outright
DELETE FROM UserRole WHERE userId = 'suspicious-user-id';
DELETE FROM User WHERE id = 'suspicious-user-id';

Step 5 — Check for planted content

Attackers commonly insert hidden posts, scripts in widget text, or malicious settings values.

-- Recently created or modified posts (check for injected content)
SELECT id, title, status, type, createdAt, updatedAt
FROM Post
ORDER BY updatedAt DESC
LIMIT 20;

-- Widget configs that contain script tags or iframes
SELECT w.name, ws.value
FROM Widget w
JOIN WidgetSetting ws ON ws.widgetId = w.id
WHERE ws.key = 'config'
  AND (ws.value LIKE '%<script%' OR ws.value LIKE '%<iframe%');

-- Settings that may have been tampered with
SELECT key, value FROM Setting
WHERE key IN ('site_logo', 'site_logo_dark', 'admin_email')
ORDER BY key;

Step 6 — Review access logs

Identify the entry point — was it a stolen credential, a brute-forced password, or exploitation of a vulnerability?

# Express/Node logs (if using systemd)
sudo journalctl -u headtilts-api --since "2 days ago" \
  | grep -E "POST /api/auth|PUT /api/users|DELETE"

# nginx/Apache access log (if behind a reverse proxy)
grep "POST /api/auth/login" /var/log/nginx/access.log \
  | awk '{print $1}' | sort | uniq -c | sort -rn | head -20

# Look for unusual IPs that hit admin endpoints
grep "/api/" /var/log/nginx/access.log \
  | awk '{print $1, $7}' \
  | grep -v "^YOUR_KNOWN_IP" \
  | sort | uniq -c | sort -rn | head -30

Step 7 — Restore from backup (if needed)

Only required if the attacker deleted or corrupted data. If they only read data, restoration is not needed (the data is gone regardless). Follow the Restore Procedure steps above, using the most recent clean backup — typically the one from before the intrusion timestamp you found in the logs.

Step 8 — Bring the site back online

# Ensure .env (root) has all new credentials
grep -E "JWT_SECRET|DATABASE_URL|SMTP" .env

# Re-open the firewall
sudo ufw allow 3000
# or
sudo iptables -D INPUT -p tcp --dport 3000 -j DROP

# Start the application
sudo systemctl start headtilts-api

# Monitor logs for the first 10 minutes
sudo journalctl -u headtilts-api -f

Step 9 — Post-incident review

Once the site is stable, conduct a short review:

  • Document the timeline: when access was gained, what was accessed, when it was detected.
  • Identify the root cause and patch it (weak password, reused credential, unpatched dependency, misconfigured firewall).
  • Notify affected users if personal data (emails, names) was accessed — this may be a legal requirement under GDPR or equivalent.
  • Increase backup frequency or retention window temporarily.
  • Enable two-factor authentication on admin accounts if not already done.
  • Review and tighten firewall rules — the API port should only be accessible via a reverse proxy, not directly from the internet.
